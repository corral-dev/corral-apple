# Native macOS client design

Status: v1 (phone-derived layout) shipped 2026-10-04. **Superseded in direction the same day by the [desktop-first redesign](#desktop-first-redesign-owner-requirement-2026-10-04-round-2)**: the Mac follows the desktop TUI, not the phone. Sections below that describe phone-derived interaction (sidebar sections, inspector, bubble cap) are the v1 record, not the target.

Current sidebar authority: [Flat session sidebar](#flat-session-sidebar-owner-decision-2026-10-15) supersedes all older split-card, group-disclosure and member-indentation presentation rules in this document. Shared host split persistence/restoration remains in force.

## Owner requirement (2026-10-04)

Build a native macOS Corral client that:

- uses current native macOS UI APIs wherever they exist (SwiftUI first, AppKit only where SwiftUI has no public equivalent);
- reuses the existing iOS code as much as possible, restructuring it where needed so both apps share one implementation;
- stays clean and light like the current iOS client (same Pine palette, official assistant logos, status dots, sage user bubbles);
- borrows proven desktop chat patterns from the Codex and Claude desktop apps;
- has visible entry points for Corral's own distinctive features.

This **replaces the Mac Catalyst step** in [iPad and Mac client adaptation](MULTIPLATFORM_CLIENT_DESIGN.md). The product rule there still holds: every Apple client is a remote client of a Corral host and never runs agents locally, even on a Mac.

## Why native SwiftUI, not Catalyst

The earlier Catalyst choice assumed an existing iPad/UIKit app. Corral iOS is SwiftUI-first instead:

- 13 of about 90 source files import UIKit, and most only use `UIFont`, `UIImage`, `UIColor` or haptics. The only substantial UIKit view is the selectable message text (`UITextView`). Only 14 call sites use iOS-only SwiftUI modifiers (`navigationBarTitleDisplayMode`, `.topBarTrailing`, `.bottomBar`, keyboard dismissal, detents).
- About 45 files (protocol, crypto, connection, stores, conversation/send/timeline logic, list filtering) already compile and test on macOS through `Package.swift` (284 portable tests).
- Apple's current guidance: Catalyst exists to bring an iPad app to the Mac; a SwiftUI app should add a macOS target and share code ([Apple forums, State of Mac Catalyst in 2026](https://developer.apple.com/forums/thread/811728); [multiplatform recommendation](https://developer.apple.com/forums/thread/651050)). Home Assistant moved its Mac app from Catalyst to native for the same reasons ([PR #5934](https://github.com/home-assistant/iOS/pull/5934)).
- Only a macOS target gets the Mac scene types and behaviors this design depends on: `Settings`, `MenuBarExtra`, multiple windows/tabs, the inspector column, and the Mac toolbar and menus.

Codex and Claude's desktop apps are both Electron. A truly native Corral (system sidebar, toolbar, search, menus, windows, VoiceOver and keyboard behavior) is a visible differentiator, not just an implementation detail.

## Window and layout

Minimum system: macOS 26 (the Liquid Glass design generation). macOS 27-only APIs are availability-gated.

```
┌ Sidebar ────────────────┬ Conversation ───────────────────────────┬ Inspector (⌥⌘I) ─────┐
│ [● the paired Mac ▾]  [✎]  │ Fix relay timeout                [⇄] [ⓘ]│ Claude · Corral       │
│                         │ Claude · ~/Codes/Corral                 │ ~/Codes/Corral   ⧉    │
│ NEEDS YOU            2  │                                         │ Pinned  ·  Running    │
│  ◉ Fix relay timeout    │          ┌──────────────────────┐       │                       │
│  ◉ Ship mac design      │          │ user message (sage)  │       │ YOUR PROMPTS          │
│ PINNED                  │          └──────────────────────┘       │  1  Fix the relay …   │
│  ◯ Weekly report        │  Assistant reply as plain text in the   │  2  Also handle …     │
│ TODAY                   │  readable column, no bubble             │                       │
│  ◯ …                    │  [🔧 6 steps ›]                          │ ACTIONS               │
│                         │                                         │  Continue with… ▸     │
│                         │  ┌ question surface (when asked) ┐     │  Fork · Restart · Stop│
│                         │  ● Working                              │                       │
│                         │  ┌───────────────────────────────────┐ │                       │
│                         │  │ Message Claude…            [+] [↑]│ │                       │
└─────────────────────────┴──┴───────────────────────────────────┴─┴───────────────────────┘
          sidebar search sits at the top of the sidebar; machine + connection at its bottom
```

- **Scenes.** One main `WindowGroup` with `NavigationSplitView` (sidebar + conversation) and `.inspector`; a value-based `WindowGroup(for:)` for "Open in New Window" (native window tabs come free); a `Settings` scene (⌘,). Window size, sidebar and inspector visibility are restored (baseline A5).
- **Sidebar.** A native `List(selection:)`, the same session rows as iOS (official logo badge plus the fixed three-line [row height contract](../UI_DESIGN_KNOWLEDGE_BASE.md#row-height-contract)), collapsible sections via `Section(isExpanded:)`, context menu (Open in New Window, Pin, Continue with…, Fork, Copy path, Delete), arrow-key navigation. The sidebar toolbar holds the machine switcher (name, connection dot, LAN/relay route as hard constraint 7 requires; menu lists paired machines, Pair New Machine…, Machine Settings…) and New Session (⌘N). Runtime and project filters, multi-select with the same semantics as iOS, live in a native filter `Menu` with toggles. The iOS chip rows are a phone layout and are not copied. With no machine paired, the detail column shows `ContentUnavailableView` with the pairing actions.
- **Conversation.** Shared conversation components from iOS (timeline, tool activity capsule and detail, question surface, activity cue, inline images, failure status and Retry). Assistant replies are plain text without a bubble; user messages keep the sage bubble. Content sits in a centered readable column (about 760 pt max) so wide windows do not produce long lines. Title plus `navigationSubtitle` (assistant · project). Running state appears only in the activity cue, as on iOS. Earlier history loads from a quiet "Load earlier" control at the top; trackpads have no pull gesture. Images open in Quick Look. Message text supports partial selection and Copy.
- **Composer.** The same floating rounded card as iOS, aligned to the readable column. Return sends; Shift-Return inserts a newline; Return while a Chinese/Japanese input candidate is active must confirm the candidate, never send. Images arrive via the + button (`fileImporter`), drag-and-drop onto the conversation, or ⌘V. Per-session drafts, send exclusion and failure recovery are shared with iOS. No TUI key strip.
- **Inspector.** Session facts (assistant, project path with copy, machine, pin/state), the **Your prompts** outline (click to jump), and session actions. Tool-step detail opens as a sheet, as on iOS.
- **Menus and keys.** ⌘N new session, ⌘F search, ⌥⌘I inspector, ⌘⇧O open in new window, ⌘⌥↑/↓ previous/next session that needs you, ⌘R restart session (in the Session menu, with no confirmation step, matching the TUI and iOS). Standard Edit/View/Window/Help menus.
- **Look.** System sidebar, toolbar and search glass only (functional layer). Lists and conversation content stay solid. Pine accent and asset colors shared with iOS. No focus rings (baseline A4). Light/dark mode, increased contrast and Reduce Motion supported.

## Native API map

All checked in the installed Xcode 27.0 / macOS 27.0 SDK swiftinterfaces on 2026-10-04: `NavigationSplitView`, `inspector(isPresented:)` / `inspectorColumnWidth`, `searchable` / `searchSuggestions`, `Section(isExpanded:)`, `Settings`, `MenuBarExtra`, `WindowGroup(for:)` / `OpenWindowAction`, `navigationSubtitle`, `ToolbarSpacer`, `visibilityPriority` (27), `focusedSceneValue`, `fileImporter`, `dropDestination`, `onPasteCommand` / `PasteButton`, `textSelection`, `quickLookPreview` (QuickLook SwiftUI overlay), `contextMenu`, `badge`, `onKeyPress`, `userActivity` / `onContinueUserActivity`, `defaultLaunchBehavior`, `restorationBehavior`, `glassEffect` / `ConcentricRectangle` / `backgroundExtensionEffect` (SwiftUICore). AppKit only where SwiftUI has no public equivalent: `NSTextView` for selectable rich message text (the `UITextView` counterpart), `NSDockTile` badge. Official basis: [Build a SwiftUI app with the new design](https://developer.apple.com/videos/play/wwdc2025/323/), [What's new in SwiftUI, WWDC26](https://developer.apple.com/videos/play/wwdc2026/269/), [WWDC26 SwiftUI guide](https://developer.apple.com/wwdc26/guides/swiftui/).

Known platform limits: SwiftUI `Text` selection on macOS covers partial selection inside one view, but not across views ([Nil Coalescing](https://nilcoalescing.com/blog/EnableTextSelectionForNonEditableText/)). The Mac therefore uses an AppKit text network for continuous selection across message blocks; see [Message selection and Copy](#message-selection-and-copy-owner-correction-2026-10-07). macOS 27 changed the sidebar from floating to full-height ([MacRumors](https://www.macrumors.com/2026/06/09/macos-golden-gate-liquid-glass/)); use the system sidebar and do not style it by hand.

## Code reuse architecture

One repository (`corral-apple`, which now holds all Apple clients) and two app targets that compile shared source folders. Swift files are not duplicated, and no `public` access churn is needed.

```
apple/
  Shared/Core/       Foundation-only: Crypto, Models, Network, Protocol, Store, Conversation (send/timeline/tail cache),
                     Presentation (list filtering and display policies), Push, Terminal, Util
                     (AppStorageLocation: Application Support on iOS, ~/.config/corral-mac/ on the Mac)
  Shared/UI/         cross-platform SwiftUI: AppModel, ProductFeatures, Chat (bubbles, markdown, tool activity,
                     questions, selectable text), Composer, Sessions (rows, filters, new-session sheet),
                     Design (palette, spacing, typography, haptics)
  Shared/UI/Platform/ thin adapters: PlatformFont/Color/Image, pasteboard, toolbar placement, chat layout
                     metrics, inspection launch options; selectable text lives in Shared/UI/Chat
  iOS/               iOS shell: app, navigation stack pages (hosts, session list), camera pairing, APNs registration,
                     the phone's gated terminal grid
  macOS/             macOS shell: scenes and menus, sidebar, split panes and workspace, terminal view (SwiftTerm),
                     full-text search, Settings, pairing
  NotificationService/ iOS notification extension; compiles only RemoteCrypto, HostKeychain and the string catalog
  Tests/             unit tests (Xcode CorralTests target; Foundation-only subset also runs under SPM)
  Package.swift      portable test harness: `swift test` over Shared/Core
```

The iOS and Mac app targets in `project.yml` both compile all of `Shared/`; each adds only its own shell folder. SwiftTerm is a package dependency of the Mac target only. Share of source as of Mac 0.3.3: `Shared/` about 16k lines, `iOS/` about 2.8k, `macOS/` about 3.5k.

- **Order.** (1) A pure file move into `Shared/Core` with no behavior change; the classification already exists in `Package.swift`. (2) Extract the cross-platform views into `Shared/UI`, replacing UIKit types with adapters and fixing the open debts in [the code-quality baseline](MULTIPLATFORM_CLIENT_DESIGN.md#code-quality-baseline-2026-10-01): split `SessionListView` / `SessionDetailView` into page shell and shared parts, and compute the long-bubble cap from the container height instead of `UIScreen`. (3) Add the `CorralMac` target to `project.yml`. Every step must keep the installed iOS app behaving identically, verified on the paired iPhone.
- **Rejected:** a single multiplatform target (iOS has the NSE, push entitlements and its own Info.plist, so separate shells are cleaner) and a separate Swift package module (it would force `public` on hundreds of declarations for no product gain now).
- **Storage.** On iOS, keep today's Application Support paths and do not migrate them. On the Mac, app-owned files (paired machines, list/tail caches, drafts, pending commands, recent combos) go under `~/.config/corral-mac/` (or `$XDG_CONFIG_HOME/corral-mac/`), as the desktop config location guide (maintainer reference, not distributed) requires, through `AppStorageLocation` in `Shared/Core/Util/`. This directory is separate from the CLI's `~/.config/corral/`.
- **Keychain.** Host keys and device identity stay in the Keychain. The iOS shared access-group literal is iOS-only. Mac access follows the Mac Keychain credentials guide (maintainer reference, not distributed) and must not depend on an entitlement that only a provisioning profile provides until APNs is actually adopted.
- **Identity.** Bundle ID `com.x0c.corral`, the same as iOS, which is Apple's multiplatform default and keeps one APNs topic if Mac push is added later. Pairing sends `platform: "macos"` (the host only displays it). The Mac app has its own version line.
- **Connection model.** v1 keeps today's `AppModel`: one active machine at a time, switched in the sidebar. "All machines" (phase 3) requires per-host connections in the shared core. That is a non-UI refactor and the only core change the Mac roadmap needs.
- **Product gates.** `ProductFeatures` is shared, but `terminalPaneEnabled` only gates the phone's terminal page inside the shared session detail. The Mac terminal view is its own pane code in `macOS/Terminal/` (2026-10-05 round 3) and resizes through `terminal.resize`; no client sends `screen.resize`. Only the five active runtimes appear (dormant Kimi stays hidden, enforced by the shared `SessionListStore`).

## Distribution and software updates

Owner decision (2026-10-08), recorded before implementation: maintain two distinct Mac distribution builds. The direct-download build uses Sparkle for automatic checks, signed downloads, installation and relaunch, with an explicit Check for Updates command and user-controlled automatic-update preferences. The future Mac App Store build must exclude the updater source, Sparkle framework, helper executables and feed configuration at build time; it receives updates exclusively through the store. Hiding the menu alone does not establish this separation. This task implements direct distribution; it does not expose an unfinished store target.

Use Sparkle's standard native user interface and HTTPS delivery. Sign both update archives and the feed with EdDSA, verify archives before extraction, and retain signing secrets only in Keychain. Developer ID archive/export must sign every nested helper before distribution; notarize and staple the application before creating its update ZIP. Publish an anonymous DMG first-install route and a stable signed feed with monotonic build numbers. If the source remains private, a public artifact-only update repository is allowed; do not expose private source or planning documents to make downloads work. Once the source becomes public, move artifacts into its own releases under the shared distribution standard.

Release preparation accepts a UTF-8 `--notes-file`, copies its text into the release receipt and reuses those exact notes for the signed feed and both release pages. Resuming a prepared release must not replace its notes. This lets subsequent feature releases describe their own changes without editing already signed feed bytes.

Existing builds without an updater need one manual installation of the first updater-enabled release. Pairing, machines, conversation cache and user preferences must survive subsequent updates. Acceptance covers the actual Sparkle check/download/install/relaunch path, archive/feed signatures, anonymous downloads, installed version and connection recovery. iPhone updates remain owned by TestFlight/App Store and the terminal CLI retains its separate existing updater.

Sources: [Apple review rule 2.4.5(vii)](https://developer.apple.com/app-store/review/guidelines/#hardware-compatibility), [Sparkle setup and security](https://sparkle-project.org/documentation/), [publishing updates](https://sparkle-project.org/documentation/publishing/), and the shared signing/distribution standard (maintainer reference, not distributed).

Implementation: the direct target pins Sparkle 2.10.0 and defines `CORRAL_DIRECT_DOWNLOAD`. Its updater source is confined to `macOS/Updates/`, using `SPUStandardUpdaterController` and an Observation model around Sparkle's KVO settings. The menu uses SwiftUI `CommandGroup(after: .appInfo)`; the existing native Settings Form contains automatic-check and automatic-install toggles. Both defaults are on and Sparkle preserves user changes. The future store target must omit the folder, dependency, compilation condition and all `SU*` keys; iPhone never links Sparkle. Official artifacts and the signed feed are in [public source releases](https://github.com/corral-dev/corral-apple/releases). The legacy artifact repository serves only the final signed migration feed. The signing account is `com.x0c.corral.updates` in Keychain.

`the maintainer release tooling` requires a clean committed whole workspace, archives/exports universal Release, verifies the main app and every nested framework/helper signature, saves notarization submission IDs, staples before ZIP creation, signs the feed and refuses rollback. Publication verifies immutable assets before marking the public source release as latest; the legacy transition feed uses its previous file SHA to reject concurrent replacement. ZIP/DMG bytes are checked through anonymous downloads before exposing the feed. Complete command logs and receipts stay under `~/.config/corral/development/mac-releases/`; use the maintained workflow's detached mode for external waits. `--prepare-only` provides the committed local-install artifact; `--publish-prepared` finishes that exact source's distribution.

### Automatic update completion (owner request 2026-10-10)

Complete the existing direct-download updater as an installed, usable feature: initialize its app-owned standard Sparkle controller at launch, check hourly by default, download signed updates automatically and install them at quit without discarding pairing, drafts or cached conversations. Explicit checking retains Sparkle's standard Install and Relaunch action. Info.plist owns defaults; user changes remain authoritative. Automatic installation must not force an active conversation to quit.

The source is now public. New official artifacts and the signed appcast belong in the public source repository's releases. Use `https://github.com/corral-dev/corral-apple/releases/latest/download/appcast.xml` as the new feed, keeping the current public key and Developer ID identity. Publish a final signed compatibility feed on the former artifact repository pointing to this transition release, then archive that repository; existing installs can migrate without a manual reinstall. Public self-builds keep their separate signing and update configuration. Maintainer publication takes `--public-source <committed sanitized checkout>` and verifies byte-identical Mac/UI Swift source before publishing its tag; it never publishes the private Git history. Release resumption must reuse accepted DMG/ZIP bytes and bind saved notarization IDs to artifact hashes rather than recreating a submitted DMG. Anonymous HTTPS reads use bounded retries for transient network errors; a missing feed remains a distinct HTTP 404, and all successful artifact reads still require matching signed bytes and SHA-256. A prepared artifact may resume after committed documentation or release-tool-only changes: retain its original compiled source commit, record the newer delivery commit, and reject any change to application source, resources, dependencies or build configuration. This preserves a reproducible artifact without repeating compilation for publication-tool repairs.

Acceptance must separately record signed anonymous downloads, automatic check/download, real bundle replacement and relaunch, installed identity and connection recovery. A locked console or denied capture remains a visual acceptance limit, even when the unattended installation path succeeds. iPhone remains on its store-owned path and the CLI on its existing updater; this Mac-only feature does not change either client.

#### In-app updater acceptance and "launching the installer" failures (2026-10-12)

The Sparkle CLI runs its own launcher, so it does not prove the app's built-in updater. Accept the in-app path without pointer driving: unpack the previous public release ZIP into a scratch folder, set `SULastCheckTime` in the shared `com.x0c.corral` defaults to more than an hour ago, launch the scratch copy with `open -n -g`, and watch `log show --info --predicate 'subsystem == "org.sparkle-project.Sparkle" OR process == "Autoupdate"'`. The app's own updater must verify the appcast, download, and start `Autoupdate` and `Updater`. Terminate only the scratch process by PID (never quit by bundle identifier: that also quits the installed client). The scratch bundle must then report the new version with a valid signature. Delete the scratch copy afterwards. Verified on 2026-10-12: public 0.3.86 (90) updated itself to 0.3.87 (91) this way on the maintainer Mac.

Sparkle shows "An error occurred while launching the installer" only when its in-process installer launcher fails (`SPUInstallerDriver`, Sparkle 2.10). Each cause first logs an error-level `org.sparkle-project.Sparkle` message: "Failed to gain authorization required to update target", "Failed to submit installer job", "auth right set" or "system domain rights" failures, or "InstallerLauncher failed to create bundle". These depend on the machine running the update, not on the published build. The common case is an app bundle the logged-in user cannot write (owned by root or another account), which forces the system-domain path that needs admin authorization. Diagnose on the affected Mac: `ls -ld /Applications/Corral.app`, `xattr -l /Applications/Corral.app`, the installed `CFBundleVersion`, and `log show --last 2h --predicate 'subsystem == "org.sparkle-project.Sparkle"'`. A release cannot be blamed until the in-app acceptance above fails for it. Distinct failure: "An error occurred while downloading the update" with CFNetwork `-1200` is a TLS failure through the local proxy to `release-assets.githubusercontent.com` (seen on 2026-10-12 on the maintainer Mac). Do not confuse the two.

### Local host setup in pairing (owner request 2026-10-13)

Problem: the Mac client only reaches a development machine that runs the Corral CLI's remote service. - **Workspace.** `MacWorkspace` owns up to four pane keys, the focused pane, the board and the shared layout. Clicking a sidebar session opens its visible group (members as panes, that one focused) or replaces the workspace with it; "Open in Split" / ⌘D add a pane; the pane ✕ / ⌘W close it (leaving its group, which dissolves below two). Two or more panes call `layout.setGroup`; focus changes call `layout.setFocus`. Clicking anywhere in a pane focuses it (a local mouse monitor, so clicks still reach text and controls); the focused pane's header is tinted.
- **Pane.** Header: attention dot, assistant badge, title and project (titles give way first so four panes fit), Chat / Terminal segmented control, session menu (pin, fork, continue with another assistant, restart, stop, copy path), close. The pane owns the session's `ConversationStore`, injected into the shared `SessionDetailView`, so the prompts panel stays live in both views. Stores start only on a ready connection and rebind when the app replaces its client; a first load that races the data-plane attach retries.
- **Prompts panel (superseded by the [prompts card](#prompts-card-owner-request-2026-10-05)).** The TUI session HUD per pane, oldest to newest, time column `HH:mm` / `MM-dd`, floating at the pane's top trailing corner.
- **Terminal view (superseded in round 3, below).** `screen.watch` frames drawn by an AppKit view (wide CJK cells on their tmux columns, 256-colour and truecolour, cursor block when focused). Font is the largest of 11–15 pt that fits the host columns; wider host panes scroll sideways (horizontal wheel), vertical wheel scrolls host history (`screen.scroll`) with a Back to Live button. Keys: `TerminalKeyMapping` (Enter, S-Enter, Tab/BTab, BSpace, DC, arrows, Home/End/PageUp/PageDown, F1–F12, Control and Option-as-Meta combos); text through `NSTextInputClient`, so input methods compose locally; ⌘V pastes; input is serialized and coalesced. Every input carries a `command_id`. An unhosted session shows a restart prompt; Return restarts natively.
- **Sidebar.** `DesktopSidebarProjection` (portable, tested): Active sessions entry, pinned block, local-calendar buckets (today, yesterday, weekday names, earlier collapsed), group cards (pin mark, project, member count, collapsed attention summary; collapse syncs through `layout.collapse`), stable first-seen order, local filter (title, project path, group name). The phone's runtime/project filter chips are gone. Row geometry follows the [sidebar density redesign](#sidebar-density-redesign-owner-request-2026-10-05); the iOS three-line row is not used on the Mac.
- **Chat on the Mac.** Messages are never height-capped; tool steps open in a native popover anchored to the Agent Activity capsule ([Agent Activity contract](../UI_DESIGN_KNOWLEDGE_BASE.md#mac-agent-activity-popover-2026-10-07)); v1 inspector removed (pane header plus prompts panel replace it).
- **Search.** ⌘F opens a panel over `search.fulltext`, hit lines highlighted, Return or click opens the session.
- ~~**Board.**~~ Removed 2026-10-11 (with ⌘0 and ⌘[ / ⌘]); replaced by the [Active quick filter](#active-quick-filter-selection-clarity-and-capsule-new-session-owner-request-2026-10-11).
- **Shortcuts.** ⌘N new session, ⌘D add pane, ⌘W close pane, ⌘E chat/terminal, ⌥⌘P pin, ⌘1–⌘4 focus pane, ⌘F search, ⌥⌘↑/↓ next/previous session waiting for an answer, ⇧⌘N pair.

### Terminal view rebuild (owner decision 2026-10-05, round 3)

Owner report on Mac 0.2.1: the terminal view did not adapt to the window size and scrolling an agent TUI stuttered. Causes of the round-2 renderer: the host pane was never resized (font scaled to fit, wide panes scrolled sideways); every frame redrew every cell with `NSString.draw`; each wheel step was a `screen.scroll` round trip plus a full recapture. The owner approved the recommended rebuild:

1. **Emulator: SwiftTerm** ([repository](https://github.com/migueldeicaza/SwiftTerm), MIT, pinned release), its AppKit `TerminalView` hosted in the pane. Scrollback, selection, and copying are local; drawing uses SwiftTerm's CoreGraphics renderer (Metal was on in 0.3.0–0.3.2, dropped for the reason in [Terminal keyboard focus](#terminal-keyboard-focus-and-early-snapshot-owner-report-2026-10-05)). Known limit: parsing and drawing share the main thread, so very heavy output can still cost frames ([issue 137](https://github.com/migueldeicaza/SwiftTerm/issues/137)). tmux itself also slows under heavy output ([iTerm2 note](https://gitlab.com/gnachman/iterm2/-/issues/7899)).
2. **Raw stream from the host.** The host reads the pane's output through its tmux control-mode client (`%output`, the bytes the agent wrote) and forwards them in order on the data plane, coalesced to about 60 updates a second. A client starts from a host snapshot, and any gap or size change brings a fresh one. The snapshot covers recent history, the visible screen, cursor, the alternate-screen state, and the cursor-key, keypad, and mouse modes. Snapshot and stream are ordered on the same control client, so no output is lost or doubled. tmux answers terminal queries itself; the Mac emulator's own replies are dropped.
3. **Sizing like a TUI window.** The Mac reports the columns and rows its pane fits at the base font, and votes in the same viewer registry the TUI windows use. Since 2026-10-12 the host resizes the pane to the **most recently used** viewer's grid ([Terminal size follows the client in use](#terminal-size-follows-the-client-in-use-owner-decision-2026-10-12)); the earlier widest-width / tallest-height rule is superseded. When another viewer's grid is in charge and larger, the Mac shrinks the terminal font to fit the shared grid (down to 9 pt) and crops only what still does not fit: the right edge and the top, never the bottom where the agent's input sits (owner report 2026-10-05: cropping looked like the TUI overflowing). The terminal pane never imposes its grid as a minimum width on the split; while the window or a divider is being dragged the grid only moves, and the fit and size vote are sent once the drag ends. The vote is refreshed while the pane shows the terminal and dropped on detach or disconnect. Read-only devices watch without voting. The phone keeps the snapshot frames (`screen.watch`) and never resizes.
4. **Input.** Keys and input-method text go to the pane as raw bytes (`terminal.input`), serialized and coalesced, under the terminal typing limit. Paste goes through the host paste path (`input.text`, no submit, with a `command_id`), so bracketed paste follows the agent's real mode. Wheel and mouse events follow the agent's mouse mode: local scrollback when the agent did not ask for the mouse. Mouse reports leave only the focused terminal of the key window: Claude Code tracks every pointer move, and hovering over a background pane must never type into it. The wheel is the exception: it reaches the terminal under the pointer ([Wheel scrolls the terminal under the pointer](#wheel-scrolls-the-terminal-under-the-pointer-owner-report-2026-10-06)).

Host methods (capability `terminal_stream`): `terminal.attach`, `terminal.resize`, `terminal.input`, `terminal.resync`, `terminal.detach`; events on channel `term:<session>`. Wire details: the CLI remote knowledge base, "桌面终端原始流".

Implementation (Mac 0.3.0, CLI 0.24.256, 2026-10-05):

- **Host.** `remote/terminal_stream.py`, one stream per watched session on the remote service's tmux control client: snapshot plus ordered output with the `output_seq` barrier, 60 Hz coalescing, events capped at 256 KB, a backlog over 8 MB replaced by a fresh snapshot, a one-second tick that renews size votes, follows resizes made by other viewers and rebinds after a native restart (or reports `ended`).
- **Mac.** `RemoteTerminalStream` (attach once the pane knows its fit, 150 ms settle before re-voting, gap → resync, backlog until the view exists) and `TerminalEmulator` (SwiftTerm `TerminalView` subclass, SF Mono 13 pt, dark palette; light and dark since 0.3.21, see [Terminal follows the system appearance](#terminal-follows-the-system-appearance-owner-report-2026-10-06)). The view frame is exactly the host grid, so the emulator's own grid always matches tmux; a wider host grid is cropped top-left. Emulator replies produced while drawing host bytes are dropped.
- **Workspace fixes found in acceptance.** Background layout syncs (group, focus, pane removal) no longer raise an alert when a reconnect interrupts them; connection errors show their own text instead of "Unknown error". Relaunch restores the last panes without writing a group, so a split changed in the TUI meanwhile is not overwritten.
- **Build.** SwiftTerm 1.20.0 through XcodeGen `packages`; command-line builds pass `-skipPackagePluginValidation` (SwiftTerm ships a build-info plugin) and need Xcode's Metal toolchain component.

Verification (Debug build against the real host, inspection arguments only, no pointer or keyboard driving): Codex's and Claude Code's own TUIs rendered by SwiftTerm at the pane's width; opening the disposable acceptance session in a split resized its tmux pane from 91 to 43 columns and Codex reflowed to the new width; with the desktop TUI showing a session wider, the Mac pane cropped instead of narrowing it; typed text (with CJK) reached Codex's composer through `terminal.input` and was erased with DEL, nothing submitted; about 15% CPU for the Debug build while a Claude Code pane streamed. ### Terminal size follows the client in use (owner decision 2026-10-12)

Owner report: with a Mac pane switched to the agent's terminal, resizing the Mac window did not resize the agent; it kept following the TUI window. - **Who counts as in use.** A user action at that viewer: typing, pasting or clicking into the terminal, opening the terminal for a session, resizing the pane while its window is key, or the window becoming key. ### Motion design (owner request 2026-10-05)

Owner request: optimize the Mac client's motion. Before this change the Mac shell had no motion of its own: panes appeared and vanished, focus, chat/terminal and the prompts panel switched in one frame, and board pages swapped without direction.

Rules (global motion guide (maintainer reference, not distributed) applied to this window):

- **Frequent actions stay instant.** Selecting a sidebar session, replacing the workspace with another session, typing, terminal output and the arrival of messages are not animated; system controls (sidebar, sheets, menus, segmented control, window) keep their own motion. Apple: avoid making people watch unnecessary motion on every interaction ([HIG Motion](https://developer.apple.com/design/human-interface-guidelines/motion)).
- **Motion explains a spatial or state change.** Adding or closing a split pane, moving focus, switching a pane between chat and terminal, opening the prompts panel or tool steps, turning a board page and switching search between hint, results, no results and failure.
- **Utility springs without bounce**, short and interruptible: SwiftUI springs retarget from the current value and velocity ([WWDC23 Animate with springs](https://developer.apple.com/videos/play/wwdc2023/10158/)). Effect properties (opacity, colour) never overshoot.
- **One token set** in `macOS/Design/MacMotion.swift`; no animation literals scattered through views.

| Change | Motion | Reduce Motion |
|---|---|---|
| Pane added (⌘D, Add pane, Open in split, fork, continue with) | Widths change at once; the new pane slides in from the split's trailing edge while fading in, and panes whose slot moved glide from their old slot (about 0.34 s) once the new pane has been built. A pane that replaces the focused one in a full split fades in place | Fade only, no travel |
| Pane closed (✕ / ⌘W) | The closed pane fades out in its slot (about 0.14 s), then the remaining panes take the space and panes whose slot moved glide there | Fade out, then instant |
| Focus moves to another pane | Header tint fades (about 0.15 s) | Same (a colour change is the accessible substitute) |
| Attention dot changes or appears in a pane header | Colour fade; appearing dot fades in | Same |
| Chat ↔ terminal in a pane (segmented control, ⌘E) | Crossfade (about 0.18 s), which softens the light-to-dark jump | Same crossfade |
| Prompts card open / close | Card grows from its top trailing corner, conversation shifts aside when the card sits beside it (about 0.24 s) | Instant |
| Jump to a prompt (prompts card) | A prompt within about 30 rows glides there, centred (about 0.45 s); a farther one fades out, moves and fades back in (shared rule in the UI design knowledge base) | Fade only |
| Tool steps expand inline | Steps fade in as the column opens, chevron turns (about 0.24 s) | Instant |
| Board page (⌘[ / ⌘]) | The old page leaves at once; the new page's panes slide about 24 pt in from the side they come from while fading, once built | Fade only |
| Search result states | Crossfade between hint, results, no results and failure; result rows themselves are not animated while typing | Same crossfade |

Split motion round 2 (owner report 2026-10-07: "opening a new split has no animation; other operations jump"). The first round's 0.2 s fade of the new pane read as no motion, because the existing panes jumped to their new widths and a closed pane vanished in one frame. Panes now travel by a render-time horizontal offset ([SwiftUI offset is drawn after layout and does not move the frame](https://fatbobman.com/en/posts/layout-dimensions-2/)): the workspace sets each moved pane's offset to its old slot in the same update as the layout change, then animates the offsets to zero one frame later, so widths still change once and nothing refits per frame. The slot positions are equal shares of the measured split width. Each hairline divider travels and fades with the pane after it. A closing pane stays drawn, ignores input and is hidden from accessibility while it fades; a sidebar selection, machine switch or relaunch restoration cancels pending exits and glides. Offsets animate through an explicit transaction, not a scoped `animation(_:body:)` modifier, because the scoped form has a known offset bug ([Apple Developer Forums 748852](https://developer.apple.com/forums/thread/748852)).

Round 2 verification (2026-10-07, Debug build of the shipped source against the real host, inspection arguments only): `-CorralInspectMotion` recorded the offsets set with each change (adding a second pane: the new pane starts half the split width to the right; adding a third: the middle pane starts one sixth to the right, the new one a third beyond the edge), the glide waiting while a pane is built (a 0.42 s build left the offsets in place until it finished), closing a pane keeping it drawn while it fades, and no offset left at the end of any step. Window captures at tenfold slowdown showed the new pane sliding in from the trailing edge and the closed pane fading in its slot. The probe now waits for the host's groups before choosing sessions (it once picked a grouped session) and falls back to a third ended session in chat view when the disposable acceptance session is absent; the host layout held none of the probe's sessions afterwards. Shipped in Mac 0.3.30 (build 34), installed in `/Applications/Corral.app` by the parallel release that integrated the tree. Not exercised: pointer clicks on ✕ and Add pane, Reduce Motion. Cross-end: the iPhone has no split panes; the TUI draws its split on a character grid and has no motion layer. A Debug window launched with `CORRAL_INSPECTION_MOTION_SLOWDOWN` slows every motion token, including tool-step disclosure; the owner mistook one such acceptance window for a regression, so quit acceptance windows when the capture is done.

Audit of the remaining jumps (2026-10-07), kept as decisions: a sidebar selection, opening a split group, the board ↔ split switch and a new session that replaces the workspace stay instant (frequent navigation, HIG); sidebar group disclosure and row moves stay instant because the list is rebuilt by structure to keep row identities unique (see the each-session-appears-once fix); the project terminal panel (⌥F12) height and the window's width growth are not interpolated, since either would refit terminals and send a host resize every frame.

Pane width is never interpolated. Measured on the first build (Debug, real host, 2026-10-05): animating the re-shared width resized a terminal pane's emulator 2 to 10 times per change (one grid refit per frame) and reflowed every chat message each frame, while building a pane blocked the main thread for 0.2 to 0.5 s (chat message text views; for a terminal, about 0.4 s of SwiftTerm searching every loaded bundle for its Metal shader library, removed when the terminal view moved to CoreGraphics drawing), which swallowed most of a 0.28 s animation. So the layout changes in one step, and a pane's entrance starts only after its first frame has been committed, so it plays completely instead of being eaten by the build. Entrances run only for panes the user adds or pages to; panes opened by a sidebar click, relaunch restoration or a machine switch appear without motion.

Not animated by decision: window width growth when a pane needs more room (system window behavior), the sidebar (system list; its redraw is a separate task), connection status changes.

**Glides are visual effects, not layout (owner report 2026-10-07: "opening and closing a terminal animates strangely"; "keep motion smooth and fast").** Measured on an optimized inspection build beside a long conversation with a main-thread probe (a background thread posting to the main queue every 4 ms; immune to the throttling of a background window): adding a pane stalled the main thread 0.58–0.77 s in total and closing one 0.42–0.61 s, in steps of 100–200 ms. Two thirds of the glide cost came from `.offset`: moving a pane moved the conversation's visible rect, so its lazy stack re-placed every row on each animation frame. Rule: travelling panes (split glide, board page slide) move with `visualEffect { $0.offset(...) }`, which leaves geometry in the slot. After the change: closing a terminal 0.15 s (largest stall about 55 ms), adding one about 0.33 s, a chat pane about 0.54 s. What remains is the one-step re-measure of the neighbours' visible messages at their new width and SwiftUI's lazy-stack height correction one pass later; both scale with conversation length and are the next target (chat row measurement), not motion tokens. The prompts card margin follows the same rule: it animates only when the person opens or closes the card, never when a split change makes it stop fitting.

Acceptance: Debug-only `-CorralInspectMotion` (no pointer driving) opens an ended session, adds the disposable `corral-phone-acceptance` session as a terminal pane and a second ended session, closes them, switches chat ↔ terminal, moves focus, pages the board, then closes everything it opened (the host group dissolves) and quits. Display-link timing is only meaningful while the window is visible: a window behind other windows is throttled and reports long gaps that are not the app's work, so attribute stalls with a whole-run `sample` instead. ### Interaction cost pass (owner request 2026-10-05)

Decisions:

Terminal view keeps the emulator as the key target. A click on conversation text or on a control never steals the caret, so text selection and buttons work as before. Arrow-key browsing in the sidebar keeps focus in the sidebar. Typing into a composer (Tab or click) selects its pane. Before this, ⌘2 marked pane 2 while typed text still went into pane 1: a wrong-session send with no warning.
2. **Quiet focus marker.** The focused pane carries a thin accent bar at the leading edge of its header; unfocused headers show their title in secondary text. No header or body tint: both pane bodies keep the same background, and the green no longer reads as a status.
3. **Prompts panel is a chip until opened.** *(Superseded by the [prompts card](#prompts-card-owner-request-2026-10-05).)* Clicking a prompt scrolls the chat to it (terminal prompt rows do not jump).

5. **No instructions where an action fits.** The empty workspace shows a New Session button instead of the sentence telling people to press ⌘N.
6. **Defaults the window already knows.** New Session (⌘N, Add pane → Other) preselects the focused pane's project. Recent assistant-and-project combos can be removed from their context menu (the phone's swipe has no Mac equivalent with a mouse).

Kept as protective friction: delete confirmation and unpair confirmation. Stop and Restart stay one step, matching the TUI and iPhone (the session can be resumed).

#### Markdown tables (owner decision 2026-10-07)

Owner report: Markdown tables in Mac replies showed as `cell | cell` text lines (the 2026-09-11 phone-first rule), which reads poorly on a wide window. Decisions:

1. **Mac draws real tables.** Columns align, the header row is semibold, cells sit on thin separator lines with cell padding; text stays in the same selectable bubble text view, so partial selection, Copy and links keep working. Implementation uses AppKit's native text tables (`NSTextTable` / `NSTextTableBlock` in the paragraph style, [Apple: Using Text Tables](https://developer.apple.com/library/archive/documentation/Cocoa/Conceptual/TextLayout/Articles/TextTables.html)), drawn by the bubble's existing TextKit 1 stack; no third-party renderer (MarkdownUI is in maintenance mode, its successor Textual has open selection crashes with changing content, and the project allows one third-party package).
2. **iPhone keeps the flat form.** The phone screen is too narrow for a grid; tables stay as readable `cell | cell` rows with a semibold header (see the [UI knowledge base](../UI_DESIGN_KNOWLEDGE_BASE.md) conversation rules). UIKit has no text-table equivalent, and the phone does not get a grid view either.
3. The TUI is out of scope for this requirement.

Implementation notes: `ChatMarkdown` (Mac branch) keeps one paragraph per cell; `MacMarkdownTable` rebuilds each table at the bubble's attributed-string conversion, from the cells' presentation intents, as fixed-layout cell blocks. Column shares come from each column's single-line content width (capped at 400 pt so one long column cannot squeeze short ones), the table is content-sized up to the bubble width and shrinks proportionally beyond it; Markdown column alignment applies; missing cells stay as empty cells. Styling: first column flush with body text, 10-pt horizontal and 5-pt vertical cell padding, a 1-pt tertiary-label rule under the header and 0.5-pt separator hairlines between rows, no vertical rules, 8 pt above and below the table, and a short spacer between two adjacent tables. Rejected in the prototype: full grid lines and a filled header band (heavier than the conversation's quiet surfaces), automatic layout (spreads columns evenly and wraps short cells), and block margins (they narrowed every column).

## Global interface zoom (owner requirement 2026-10-08)

The Mac client must support application-wide Command-plus/minus zoom. Adopted range: 80–150% in ten-percentage-point steps, default 100%, persisted locally and shared by the main and Settings windows. Support Command-equals and Command-plus for increase, Command-minus for decrease and Option-Command-0 for reset; Command-0 is unbound since the Active sessions board was removed (2026-10-11). This is a Mac presentation preference, never a remote session setting or an iPhone preference. Existing conversation text size remains a relative reading preference, multiplied once by interface zoom.

Zoom changes font metrics, product icons, padding and content dimensions before layout, preserving native controls and reflow. Cover sidebar, pane headers, messages/Markdown, composer, questions/activity, search, new-session/pairing sheets, prompts cards, Settings and both terminal types. Keep pane minimum widths bounded so four panes remain reachable; content measurements and already measured physical bounds must not be scaled twice. Preserve drafts, selection where the native component supports it, scroll position and keyboard focus; never remount a session to apply zoom. On Mac, selecting conversation text pauses automatic following until the reader explicitly returns to the latest message or scrolls back to the bottom, so streamed content and zoom reflow cannot scroll the selection out of its native row. AppKit sends shared selection notifications from the first text view, which may be outside the lazy viewport; determine focused ownership across the document cohort rather than requiring the notifying view to have a window. Also release the previous programmatic latest-message anchor by marking the native `ScrollPosition` as user-positioned ([Apple API](https://developer.apple.com/documentation/swiftui/scrollposition/ispositionedbyuser)); pausing later follow requests alone leaves that anchor active during reflow.

Public API limits: Apple states that macOS `dynamicTypeSize` does not affect text size ([documentation](https://developer.apple.com/documentation/swiftui/environmentvalues/dynamictypesize)); `Font.scaled(by:)` is available on macOS 26 in the installed Xcode 27.2 SDK ([Font](https://developer.apple.com/documentation/swiftui/font)). Native controls have discrete supported sizes ([adaptable built-in views](https://developer.apple.com/tutorials/swiftui-concepts/maintaining-the-adaptable-sizes-of-built-in-views)); application zoom does not replace or geometrically stretch system menu bars, window traffic lights, alerts, file panels or toolbar chrome. Custom product content scales, native controls select appropriate supported sizes. Commands use the native menu/shortcut APIs ([keyboard shortcuts](https://developer.apple.com/documentation/swiftui/view/keyboardshortcut(_:modifiers:))).

Toolbar correction (owner screenshot, 2026-10-08): interface zoom must preserve the system window toolbar’s native icon-button proportions, including New Session and the automatic sidebar toggle. Do not let a scaled body font or content control size replace the toolbar’s contextual defaults. Content, pane controls and reading sizes continue to zoom. Verify the complete real window at 80/100/120/150%, including the title bar; app-owned content exports do not cover toolbar chrome. Public APIs to preserve: native `NavigationSplitView`/`ToolbarItem`, contextual `font(_:)` and `controlSize(_:)` ([font environment](https://developer.apple.com/documentation/swiftui/view/font(_:)), [control sizing](https://developer.apple.com/documentation/swiftui/view/controlsize(_:))). Declarations confirmed in the installed Xcode 27.2 macOS SDK before implementation. This is a Mac-only scene/content correction; iPhone and TUI have no inherited Mac scene environment and require no behavior change. Reusable sizing findings: shared AppKit guide (maintainer reference, not distributed).

Terminal zoom changes the requested base font and corresponding size vote, not a layer transform. Preserve the latest-used-viewer contract: while another viewer's larger grid is in charge, fit can limit the visible font increase. Keep the bottom input row visible, refresh the snapshot after a font change and coalesce rapid changes. Do not override another viewer's size to force zoom.

At large zoom in narrow splits, the product pane header may reflow identity and native controls into two rows so every action remains reachable without widening a pane beyond its slot.

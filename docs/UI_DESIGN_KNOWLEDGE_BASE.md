## 重绘工作流（强制）

视觉方向**一旦在方案里锁定**（例如已选定「延续桌面端开发者气质 + 系统原生骨架」），后续执行：

1. **直接改 SwiftUI**，以本文件令牌与结构约定为合同；用模拟器/真机截图验收，不要再用图像模型批量出探索图。
2. 用户打断出图、抱怨连环生成、或说「别出图了」→ **立刻停掉一切图像生成**，转入实现，不得再开下一轮并行出图。
3. 仅当方向仍未拍板、且用户明确要求「先看效果图」时，才做出图；每次最多推进一张屏的一个方向，先给人看过再继续——禁止一上来并行三套列表 × 三套详情。
4. The approved Corral brand identity is the forest-green and warm-yellow cowboy hat with the Floral 04 cream floral background (owner decision, 2026-10-01). Use `iOS/Assets.xcassets/AppIcon.appiconset/AppIcon.png`, synchronized byte-for-byte from the canonical CLI `brand/AppIcon-1024.png`. Preserve the accepted composition, hat geometry and palette; the retired arrow, horse and unicorn designs must not return. The shared brand contract and README derivatives are owned by [Public presentation](https://github.com/corral-dev/corral/blob/main/docs/PUBLIC_PRESENTATION_GUIDE.md). Keep the app master square and opaque; the README owns its separate rounded display image.

## Mac Agent Activity popover (2026-10-07)

Owner decision (2026-10-07, supersedes the same-day inline disclosure): on the Mac, clicking the compact Agent Activity capsule opens the tool details in a native popover anchored to that capsule. The conversation never changes height, so no preceding or following message moves, and the system supplies the open/close motion. The owner rejected the inline version because collapsing required finding its top header or bottom Collapse button, opening and closing shifted the conversation slightly, it had no motion, and the expanded panel looked unfinished.

- Hit region and reflow (owner report 2026-10-10): the entire visible capsule must open its popover, including its center and lower edge; neighboring message text must not intercept it. Changing interface zoom or window width must keep visible conversation text drawn and preserve the reading position, without requiring a scroll to recover. Keep native cross-message selection and the stable conversation hierarchy. Use the public native borderless Button style for the Mac capsule, keep the pressed/open overlay noninteractive, and let native size-change anchors own Mac reflow rather than issuing new explicit latest-message scrolls from geometry callbacks. Invalidate retained native message displays when typography changes. These are compatibility corrections; the original macOS 26 reproduction remains unverified on the current macOS 27.2 host. Native hit probes use the tested view’s superview coordinates. Preserve the native popover and cross-message selection.
- Collapsed state: the existing compact summary capsule (icon, "Agent activity", tool count, trailing chevron) uses a native borderless button. It shows a pressed/open state while its popover is visible and never changes size. Keep its existing neutral label colors: the native button must use the system label tint, so hierarchical secondary/tertiary styles do not inherit the application’s green accent. The owner rejected the green regression in the 2026-10-10 screenshot; fixing the hit area does not authorize a color change.
- Dismissal: clicking anywhere outside the popover or pressing Esc closes it (the system's transient popover behavior). Clicking the capsule again also closes it. No in-content Collapse button.
- Popover content: a fixed readable width and a height that hugs short content up to a cap, scrolling inside beyond that. A short header names the group and its tool count. Each tool is one row (icon, tool name, up to two summary lines) separated by dividers, with its input behind an individual Details disclosure and its output in a code surface. Tool text stays selectable; Details expansion animates inside the popover only.
- Preserve on-demand detail loading with a progress indicator and the existing unavailable-detail error copy.
- Only one popover at a time (system behavior); opening another capsule closes the previous one.
- Placement (owner report 2026-10-08: the popover appeared on one side, collapsed and reopened on another): the popover prefers the capsule's trailing side and has a fixed width, so height changes only grow it vertically around the capsule and never flip it above/below. Its first frame already has the content height (the scroll view's ideal height up to the cap, not a measured-after-open height), and tool bodies start loading when the pointer hovers the capsule so details normally arrive before it opens.

Scope: Mac only. iPhone keeps its large native detail sheet with drag-to-dismiss and an explicit close control (contract below). The TUI shows the hosted runtime terminal and has no matching Corral Agent Activity capsule.

Compatibility acceptance (2026-10-10): the mounted production capsule resolves nine interior hit points to its native NSButton, at 80/100/150% with short and 120-message conversations and widths 420–760 pt. Native text has drawable glyphs after each reflow; the latest message remains visible, selected history remains selected and in view. Real WindowServer captures of the mounted controls show neutral grey despite an inherited green tint; a native button action opens its actual SwiftUI popover. Fixture data/detail services and unlocalized fixture copy do not establish host transport or physical macOS 26 pointer behavior. The host is macOS 27.2; the reported macOS 26 runtime is unavailable. Installed-window acceptance is recorded after delivery. Cross-client inspection: iPhone has its independent sheet/button path and no Mac interface-zoom preference; TUI uses its native runtime terminal and has neither capsule nor client transcript renderer.

Public API basis: SwiftUI [popover(isPresented:attachmentAnchor:arrowEdge:content:)](https://developer.apple.com/documentation/swiftui/view/popover(ispresented:attachmentanchor:arrowedge:content:)), which on macOS presents a transient popover that closes on an outside click ([NSPopover.Behavior.transient](https://developer.apple.com/documentation/appkit/nspopover/behavior/transient)); [DisclosureGroup](https://developer.apple.com/documentation/swiftui/disclosuregroup) for per-tool Details; [ScrollView](https://developer.apple.com/documentation/swiftui/scrollview) for long content.

Verification (Mac 0.3.52 (56), source `b13799c`, [mac-v0.3.52](https://github.com/corral-dev/corral-apple/releases/tag/mac-v0.3.52), installed at `/Applications/Corral.app`): in the installed Release, a pointer click on a 15-tool capsule in the right pane of a two-pane split opened the popover on the capsule's leading side (no room on the trailing side), arrow on the capsule, list at the top with every Details closed. In the same-source Debug build, a full-width pane opened the popover on the trailing side and settled without moving its anchored edge; a pointer click opened it with the conversation unchanged behind it and Esc closed it. Outside-click dismissal is the system transient behavior and was not separately confirmed, because the owner was using the same window concurrently. 354 portable tests, Mac lifecycle regressions and localization coverage pass. The changed files add no compiler warnings; the remaining `ChatMarkdown` Sendable diagnostics are assessed in the performance knowledge base. Publication: the 0.3.52 release page carries no packages; its ZIP/DMG job was stopped once Mac 0.3.53 (which contains this popover) published its notarized DMG and ZIP. ### Bottom search: fixed trailing icon (2026-10-01)

Owner decision (supersedes the same-day scroll-collapse attempts): the session list's bottom search is always the system's minimized search icon at the bottom right; tapping it expands the system search field. Nothing switches it on scroll.

Why: the owner wanted MindDistill's smooth scroll-down collapse, but Apple only provides that transition for a real tab bar (`TabView` + `.tabBarMinimizeBehavior`). A search-only bottom toolbar has no scroll-minimize API, and switching `.searchToolbarBehavior` between `.automatic` and `.minimize` swaps instantly. Device evidence: on the paired iPhone (iOS 27) the switch showed only the two end states in sequential screenshots even inside a 3-second animation transaction. The owner rejected that jump and rejected restructuring Corral into tabs just for the animation.

Implementation: `.searchable` + `ToolbarSpacer(.flexible, placement: .bottomBar)` + `DefaultToolbarItem(kind: .search, placement: .bottomBar)` + a constant `.searchToolbarBehavior(.minimize)`. No scroll tracking. Rendering, expansion, editing, clear, keyboard placement and material belong to the system; never replace native search to change its look, size or position. Older systems keep their native fallback. The multiline conversation composer is an editor, not tab/search navigation.

Acceptance: on the installed app the icon sits at the bottom right before and after scrolling, tapping it opens the system search field with the keyboard, cancel returns to the icon, and the last row stays reachable above it.

- The Working dots animate only their own opacity and lift; they must stay locked to the label when a session opens or the window resizes (owner report 2026-10-05: dots "fell" into place on open and trailed the label during resize). Cause: `PhaseAnimator` wraps every phase change in an animated transaction, and `offset` resolves at the leaf views, so any concurrent layout move of the footer was animated with the 0.4 s curve. Rule: drive the phase from a `TimelineView` and scope the curve with `.animation(_:body:)` around opacity/offset only; do not wrap repeating cue animations in `PhaseAnimator`/`withAnimation` over views whose position the parent controls. **Cost rule (2026-10-05, measured):** SwiftUI interpolates animations in the app process every frame, so a cue that eases forever re-rendered the whole window at display rate — the Mac client idled at ~31% CPU while one session showed Working (Release build, Apple silicon), and `symbolEffect(.variableColor)` measured the same. The dots now run as Core Animation keyframes on their own layers (`MacWorkingDots` in `macOS/Design/`, `IOSWorkingDots` in `iOS/Design/`; Reduce Motion keeps static SwiftUI dots): same 0.4 s beat, ease, opacity and 2 pt lift, executed by the render server; idle CPU ~2.7% (an un-eased 2.5 Hz step measured ~2.6% but drops the approved curve). SwiftUI still positions the fixed-size dot view, so the lock-to-label rule holds. Do not reintroduce an endless SwiftUI animation (`repeatForever`, eased `TimelineView` beats, `PhaseAnimator`) for an always-visible cue. References: https://chris.eidhof.nl/post/swiftui-phase-animation-bug/ · https://swiftwithmajid.com/2023/11/21/scoped-animations-in-swiftui/

Preview size follows the network: LAN route → high (about 1600 px), relay or cellular → medium (about 1080 px), Low Data Mode or measured slow transfers → low (about 640 px), per Apple's guidance to reduce image quality on constrained paths ([isConstrained](https://developer.apple.com/documentation/network/nwpath/isconstrained), [WWDC19 Advances in Networking](https://wwdcnotes.com/documentation/wwdc19-712-advances-in-networking-part-1/)). Tapping an image is a user-initiated request: it loads a higher-quality version and opens the system Quick Look viewer (zoom/share). Previews are cached on the phone per host+session+reference. Explicit image syntax that cannot load shows a quiet unavailable placeholder; a bare path mention that does not exist on the host shows nothing. Older hosts without the capability show no images.
- **Opening a conversation must not jump (2026-10-01).** The first rendered frame of the detail page already shows the cached conversation tail (and saved draft): create the conversation state synchronously when the page appears, never behind a network call. `runtimes.list` and the live `session.watch` run afterwards and only merge in newer content. Cause of the reported spinner-then-bubbles pop: the store was created inside `.task` after `await loadRuntimes()`. Cached image previews also render synchronously on first layout so a placeholder never resizes into the image and shoves bubbles; only images not yet cached show a placeholder.
- **Header carries no running state.** The conversation header shows title + assistant name only; Running / Needs reply live solely in the activity cue above the composer.
- **Working appears the instant the user sends.** Submitting text starts a provisional Working cue immediately (before any host reply). The host also broadcasts a provisional `working` attention to every watcher as soon as the text is injected. The authoritative attention (working/waiting) takes over when it arrives; a failed send, an authoritative idle signal arriving after a short grace, or a 20-second timeout without confirmation clears the provisional cue. The cue is shown even if the list snapshot still marks the session ended, because sending resumes it.

## Conversation alignment (WeChat-style, 2026-09-14)

Acceptance must compare the first bubble with the actual scroll viewport's top inset, including asynchronous insertion and a live activity cue; an assertion that the bubble lies anywhere in the upper 45% of the screen admits the reported middle-of-screen defect.

Keyboard returns to latest (owner requirement 2026-10-13, iPhone): whenever the composer gains focus and the keyboard comes up — tapping the field, the new-session auto-focus, or any other path — the conversation returns to the latest messages, even if the reader had scrolled up into history. `SessionDetailView` requests latest on the focus change; the overflow rule above still applies, so a short transcript stays at its top rest. ## Send white-screen (2026-09-14)

Symptom: after sending, the conversation blanks and the messages sit above the viewport; a small drag restores them. Cause: the send path issued a raw bottom-edge scroll unconditionally. With no overflow there is nowhere to go, and a stale content measurement parks the viewport past the content. Fix: after valid measurements confirm overflow, sends scroll to the layout-anchored latest id (`ChatView` passes the last timeline item, or `prompts` while pinned) via `ChatScrollView(latestID:)`; the raw edge is only a fallback when the id is missing. Short content stays under native top alignment without an explicit latest scroll. Regression: `ChatTopAlignmentLayoutTests` (overflow policy + top rest + no deep bottom offset) and `testShortConversationStaysAtTopOverKeyboard` (top rest, keyboard-cycle stability, scrollable tail grows downward without stranding content above).

## Initial conversation margins

The conversation must use the same symmetric page margins on first entry, after history arrives, and after scrolling. Scrolling must never be required to correct a left-shifted initial layout.

With the previous padded lazy stack and initial bottom scroll position, the iOS 27 runtime reported a horizontal content offset of 16 points on first insertion, placing bubble text at x=12 instead of x=28. History navigation reset the offset to zero and restored the margin. Initialize scroll position in automatic mode (`ScrollPosition(idType: String.self)`) and let `defaultScrollAnchor` own initial placement. Changing margins alone still reproduced the initial shift; an explicit initial edge position overrode the horizontal inset. Let the scroll view own page insets through `contentMargins(Space.base, for: .scrollContent)` in both supported scroll implementations; do not pad the target stack or add a delayed corrective scroll. Official API rationale: [Apple: margins and safe area](https://developer.apple.com/videos/play/wwdc2023/10159/).

The runtime regression inserts variable-height messages after the empty screen mounts, then checks visible message positions before scrolling, after selecting history, and after returning to latest. ### Agent question diagnosis and acceptance (2026-09-29)

#### Submission and draft recovery (2026-09-30 review)

- Native question submission and ordinary text/image sending share one synchronous exclusion gate. Pass the actual host readiness to the chat; an omitted readiness argument must not make an offline question actionable. While a question is submitting, freeze its answer controls so visible answers still describe the submitted payload. Failed delivery preserves the question draft for an explicit retry. Choice/disclosure controls have a visible pressed response, and disclosure animation respects Reduce Motion.
- A failed send must preserve text entered after the composer was cleared. Restore the failed text before the newer draft instead of replacing that draft. Retrying a failed bubble must not clear an unrelated composer draft, and a failed bubble retry must leave the draft text untouched: the retry never removed composer text, so its failure must not prepend the bubble payload again (if A fails while B is typed, the draft holds A plus B; a failed retry of A keeps that draft instead of duplicating A). Only a send that cleared the composer restores its payload on failure. For multiple attachments, restore only the failed/not-yet-attempted suffix; confirmed successful attachments must not return to the composer and be sent a second time. A transport error does not establish that the failed image was undelivered: retain that attachment's command ID and reuse it on explicit retry when the host supports receipts, never retry automatically. Older hosts without receipts cannot resolve ambiguous image delivery; duplicate avoidance is not established for them. Stage the optional local text bubble immediately when image sending starts, before waiting on uploads; if an image fails before text transmission starts, that text is definitely unsent rather than an ambiguous delivery.
- Source evidence: the pre-review detail used the chat's default `isConnected = true`, submitted questions outside `isSending`, replaced `draft` on failure, and restored the entire image array after partial success. ## 会话输入交互（强制，对标常见聊天软件）

覆盖「键盘弹出后对话没跟着上移 / 输入条被键盘挡住 / 连点发送重复发出 / 翻历史时被强行拉回底部 / 输入框上下键翻不出历史消息」。误修风险：只改输入框样式，漏掉键盘避让、贴底跟随和发送互斥。

验收对象是**会话详情里的输入条 + 对话列表**。终端重新上线后，终端页若共用同一条输入，键盘同样不得挡住输入。不要用无键盘的静态预览冒充。

1. **Keyboard and composer ownership (2026-09-11 rewrite)**: use native SwiftUI keyboard safe-area avoidance. `ChatScreen` reserves the composer with `safeAreaInset(edge: .bottom)`; neither the screen nor conversation ignores the keyboard safe area. Do not calculate keyboard height, select a global window, merge notification/guide samples, or add compensating padding. The composer must remain above the software keyboard and below the navigation bar, including multiline text and image previews. Keep the existing native input field, send exclusion, and draft behavior. The user explicitly requested a complete rewrite using mainstream Apple APIs after occlusion, freezing, and status-bar overshoot regressions.
2. **最新内容跟着上移**：用户本来就在看最新一条时，键盘弹出、输入框变高、自己发出新消息、助手新回复到来，最后一条都必须仍在输入条上方可见。不要只把输入条顶上去、对话还停在原处。**自己发出新消息（2026-09-10）**：点发送（或点提问选项）画出本地气泡后，必须**立刻强制贴底并滚到最底部**——即使刚才在翻历史；这是明确的「看我刚发的」动作，不走「翻历史不抢位置」。
3. **翻历史不抢位置**：用户已经向上翻看更早内容时，键盘弹出或**后台**新消息（助手回复、工具卡）**不得**把阅读位置拽回底部。此时在对话区右下角给「回到最新」入口；点了之后恢复贴底跟随。例外见上条「自己发出新消息」。
4. **滑动收键盘**：在对话列表上出现滚动就立刻收起键盘（`scrollDismissesKeyboard(.immediately)`），不要跟手拖动，以免键盘半悬遮挡阅读。
5. **发送互斥**：文字发送、发图、点提问选项，在途中不可再点；发送按钮在空文案**且**无待发图、或发送中为禁用。点发送后输入框与附图预览**立刻清空**并保持键盘，方便连发；有文字时**同时立刻画出自己的气泡**。Outgoing message appearance (owner correction, 2026-10-10): iPhone and Mac use the ordinary user-message text color and full bubble opacity immediately, including while queued or sending; host confirmation must not change brightness. Delivery failures retain the ordinary bubble with the existing cause and explicit Retry below it, as specified in Send failure feedback. 失败仍把原文与未发出的图还原到输入区并显示错误条。不要等远端成功才清空，也不要等助手历史写完才出气泡。助手正式消息到达后按正文去重，禁止两条一样的用户气泡。**本地气泡位置（2026-09-10）**：刚发出的气泡必须插在「发出时已有正式消息」之后、之后到达的助手正式消息之前；禁止把所有本地负序号整段甩到时间线末尾（否则助手先到时会出现「自己先说的话排在助手后面」；退出重进只剩正式序号又看起来正常）。
6. **不要自动弹出键盘（列表点进）**：从会话列表点已有会话进入详情时不要抢焦点；用户点输入框再出键盘。**例外**：新建会话成功直进聊天时必须立刻聚焦输入（见「主界面结构约定」第 9 条）。
7. **输入框高度**：空卡已是两行（上方正文区 + 下方加号/发送）。正文区默认一行，随字数长高，最多约六行后内部滚动，不得把对话区挤没。加号和发送只按 32pt 视觉占高，行下不要再垫空白，与正文之间留一小段空隙（`Space.sm`）。禁止再把空卡拉高去填中间。
8. **发送反馈**：成功点发送给一次轻触反馈；失败走已有错误条，可再给错误触感。
9. **上下键翻历史消息（机主要求，2026-10-06）**：有实体键盘时（Mac、iPhone/iPad 外接键盘），输入框里按 ↑ 依次取出本会话自己发过的消息（与 Your prompts 同一来源、同一过滤，新→旧），按 ↓ 往回翻，翻过最新一条时恢复开始翻之前没写完的草稿。只在光标位于第一行（↑）/最后一行（↓）时接管，否则方向键照常在多行文字里移动光标；取不到光标的平台（iOS 17）只在单行文字或正在显示的历史原文未改动时接管。取出的消息只填进输入框，不自动发送、不动待发附图；发送或换会话后重新从最新一条开始翻。终端界面（TUI 与 Mac 终端视图）里的输入归各助手自己处理，不在此列。
   - 实现与验收（2026-10-06）：逻辑在 `Shared/Core/Conversation/ComposerHistory.swift`（单测 `Tests/ComposerHistoryTests.swift`），按键在 `ComposerBar` 的 `onKeyPress`；Mac 用当前输入框的文字视图判断光标所在可见行（含自动折行），输入法有未上屏的拼音时一律放行。后台窗口收不到 `CGEvent.postToPid` 发来的任何按键，切前台按键又被本仓禁止，所以验收用调试版环境变量 `CORRAL_INSPECT_COMPOSER_KEYS`（如 `draft:a\nb,up,up,down`，每 3 秒一步，经窗口真实按键分发送到选中格子的输入框；正式版没有）。真窗口实测：两行草稿光标在第二行时第一下 ↑ 只移光标，之后依次取出三条历史（含多行长消息），↓ 逐条返回并恢复草稿，未选中的格子不受影响。首发于 Mac 0.3.22 (26) 与 iPhone 1.0.118 (128)；iPhone 外接键盘路径未实测（真机无实体键盘）。

### Implementation and evidence boundaries

- `ChatScrollView` owns reading position. On iOS 18+, use `ScrollPosition`, role-specific default anchors, and scroll-phase tracking. - Do not trigger scrolling from keyboard notifications or geometry resize callbacks. There are no keyboard animation timers, repeated `scrollTo` retries, or window-attached probe views.
- Keep the conversation's scroll hierarchy stable when loading, receiving, or rendering content. Immediate dismissal stays on the system scroll view.
- Native safe-area layout must be verified at runtime; an API choice or a green build alone is not acceptance. Test software-keyboard presentation, typing, hide/reopen, multiline growth, older-message selection, and background replies. Chinese candidate-bar changes and physical-device gestures require separate evidence.
- Previous claims that `safeAreaInset` itself causes occlusion, or that a window constraint definitively caused a deadlock, were not backed by a captured failing stack/runtime comparison. They are withdrawn as general rules. The reproducible arithmetic flaw and remaining evidence are in [keyboard troubleshooting](troubleshooting/2026-08-29-chat-keyboard-does-not-lift.md).

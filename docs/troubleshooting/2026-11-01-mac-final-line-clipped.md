# Mac final message line clipped after a bold lead or heading

## Requirement and evidence

The final line of a Mac chat message must remain fully readable at every supported pane width and text size. Preserve native text selection, Markdown spacing and conversation-owned scrolling; do not add arbitrary bottom padding or change the composer.

The owner's 2026-11-01 capture shows the final Chinese sentence cut horizontally, with free space between the message and composer. The exact message starts with a bold-only paragraph. A production-source TextKit probe reproduces a drawn height 8.0001 pt greater than the detached row measurement across widths 240–826 pt and body sizes 11.2–21 pt. At 14 pt / 594 pt, the row measures 198 pt but the native container uses 206.0001 pt. This is client presentation, not SessKit history extraction or remote delivery.

## Cause and correction

`MacConversationTextDocument` starts every message after the first with a near-zero paragraph break. This preserves list first-line indentation after a container break (the [earlier list defect](2026-10-27-mac-message-first-line-list-indent.md)). TextKit honors the next paragraph's `paragraphSpacingBefore` after that break, including the 8 pt for a bold lead and 8–10 pt for a Markdown heading. A detached measurement beginning directly with the message omits that first-paragraph spacing, so the actual text exceeds the allocated row.

Measure the same boundary context as the live container: prepend the identical near-zero paragraph only when the message has a preceding block, retain the existing trailing-container-break context, and invalidate text-size and table row-height caches when either boundary changes. Never remove the paragraph-start fix or estimate the difference with a constant. Reusable native behavior and measurement guidance live in the [AppKit guide](../../../../_standards/workspace-docs/swift-docs/macos-appkit-gotchas.md#a-container-break-makes-the-next-containers-first-line-a-continuation-macos-272-2026-10-27).

Inspected references: production `MacConversationTextDocument`, `MacTextMeasurement`, `MacSelectableTextView.sizeThatFits`, `ChatMarkdown.MacRhythm`, and `scripts/mac-chat-lists/Probe.swift`. Reuse this native TextKit 1 measurement/drawing stack, not a new renderer. Public APIs are [`NSLayoutManager.ensureLayout(for:)`](https://developer.apple.com/documentation/appkit/nslayoutmanager/ensurelayout(for:)) and [`usedRect(for:)`](https://developer.apple.com/documentation/appkit/nslayoutmanager/usedrect(for:)); the latter reports current container-coordinate geometry without doing layout. Both are declared in the installed Xcode 27.2 AppKit SDK. The text view's inset remains zero.

## Cross-client scope

The affected document and measurement compile only on macOS. iPhone renders each bubble in an independent `UITextView` and measures that same independent context, with no preceding synthetic paragraph. The TUI uses terminal-cell rendering, not this multi-container network; its read-only conversation projection includes the complete final sentence. Neither requires this Mac-only boundary correction.
